# varyk-sql 0.3: concrete pools, and time, ids, and bytes

Date: 2026-10-07.

**Status.** Implemented in 0.3.0. Extends
`2026-10-03-varyk-sql-design.md` ("0.1 §n"), whose rules stay in force
except where this spec replaces them. Its compiler side is Varyk
milestone 5c (`Varyk-Lang/varyk`,
`docs/specs/2026-10-07-milestone-5c-design.md`, "M5c §n"), whose section
6.2 is the contract this spec implements. Varyk is experimental and
pre-1.0: anything here may change.

## 1. Summary and scope

Varyk 0.8 brings three types, `Time`, `Uuid`, and `Bytes` (M5c §2), and
`varyk_std::Value` gains a variant for each. 0.3 makes them columns:

```varyk
struct User {
    id: Uuid,
    name: string,
    avatar: Option<Bytes>,
    created_at: Time,
}

async fn add(db: sql::Pool, name: string) -> Result<User, Error> {
    db.one(
        "insert into users (id, name, created_at) values ($1, $2, $3) returning id, name, avatar, created_at",
        Uuid::new(), name, Time::now(),
    ).await
}
```

works on Postgres with `uuid`, `bytea`, and `timestamptz` columns, with
no cast in the query, and the same program with `?` placeholders works
on SQLite. MySQL has no `returning`, so there the row is read back with
a `select`.

sqlx's `Any` driver has no date or uuid kind, so 0.3 leaves it for the
three concrete drivers. The public surface does not change: `connect`,
`connect_with`, `Pool`, `Tx`, and their calls keep their signatures
(0.1 §2). What changes is what can be bound and read (sections 2 and 3)
and what a program no longer has to write: most of the Postgres casts
for a value that may be `None` (section 2.2), and the cast for a MySQL
unsigned integer (section 3).

### 1.1 Decisions

- **Concrete pools.** `Pool` and `Tx` hold one of sqlx's `SqlitePool`,
  `PgPool`, and `MySqlPool` and their transactions, behind a private
  enum whose arms exist only with their cargo feature. This replaces 0.1
  §1.1's first decision and answers 0.1 §9's last open question. The
  public items stay free of `#[cfg]`, which Varyk does not import; only
  private items carry it. A program built with two drivers still chooses
  between them by URL alone.
- **A `Uuid` is text on MySQL and SQLite.** Bound as its 36-character
  written form, so a user writes `char(36)` on MySQL and `text` on
  SQLite: readable in a SQL shell and in SQLite tools, the same as in
  JSON. Postgres uses its own `uuid` type. Reading accepts 16 bytes as
  well, for a table that already stores them.
- **A `Time` on SQLite is text of a fixed width,**
  `2026-10-07T12:00:00.000000Z`, so `order by` and `<` in SQL agree with
  `<` in Varyk (M5c §6.2). `varyk-sql` writes this text itself and
  reads the column as text: sqlx's SQLite encoder trims trailing zeros,
  and its decoder can panic on an integer out of range.
- **A Postgres timestamp is read as its microseconds,** an `i64` from
  the raw value, turned into a `Time` by `varyk-sql`: sqlx's decoder
  panics on `infinity` and on a time past the year 9999. One outside
  `Time`'s range is an `Error` naming the column.
- **`None` is an untyped `NULL` on Postgres,** so the server takes its
  type from the query; 0.1 sent an integer `NULL`, which made a program
  write `$1::text::boolean` for a value that may be `None`.

## 2. Binding

### 2.1 Values

| Value | Postgres | MySQL | SQLite |
|---|---|---|---|
| `Null` | an untyped `NULL` (section 2.2) | `NULL` | `NULL` |
| `Bool`, `Int`, `Float`, `Text` | as 0.1 | as 0.1 | as 0.1 |
| `Time` | `timestamptz` | a `DATETIME(6)` value in UTC | text, `2026-10-07T12:00:00.000000Z` |
| `Uuid` | `uuid` | text, 36 characters, lowercase | text, 36 characters, lowercase |
| `Bytes` | `bytea` | `BLOB` | `BLOB` |

A `Time` on MySQL is sent as a date and time with no zone, in UTC, and
the session's time zone is UTC (sqlx sets `time_zone='+00:00'` unless the
URL says otherwise), so a `TIMESTAMP` column holds the same instant. A
URL that sets another `timezone` is the program's choice, and the README
says that a `Time` is then read as that zone's wall clock taken as UTC.
A `Bytes` is copied into the driver's buffer, as sqlx's arguments own
their values; the copy is the package's, not the compiler's (M5c §3).

### 2.2 `NULL` on Postgres

A `Value::Null` is bound with type OID 0, "unspecified", so Postgres
infers the parameter's type from where it stands: `insert into users
(avatar) values ($1)` gives it `bytea`, and `update users set done =
$1` gives it `boolean`. Postgres needs that type at the parameter's
first use, so one first used where nothing gives it a type, as in
`select $1 is null` or `where ($1 is null or name = $1)`, is an error
from Postgres ("could not determine data type of parameter $1"), which
the program answers with a cast at that first use: `where ($1::text is
null or name = $1)`. The README's advice to write `$1::text::boolean`
for a value that may be `None` goes, and its `$1::text` advice becomes
the one rule above. A test proves the OID 0 binding first in the plan;
if sqlx refuses it, the spec is amended before anything else is built
on it.

### 2.3 What stays

The placeholder count check on SQLite and MySQL, Postgres statements not
kept prepared, a failed statement marking a `Tx` failed, and reading to
the end of a result on Postgres and MySQL, all as 0.1 §2.3 and §2.4.

## 3. Reading

A cell switches on the driver's own type name for the column, in place
of `Any`'s kind. A field of the three types asks for a string, as a
`string` field does (M5c §5), so `varyk-sql` does not know which of them
it fills: it hands a time column over as the written form of a `Time`, a
Postgres `UUID` as the written form of a `Uuid`, a text column as its
text, and a binary column raw (`visit_byte_buf`). The field's own
deserializer takes or refuses what it gets, and a refusal is an `Error`
naming the column. Its message is `varyk-sql`'s own, "column `x` cannot
be read into the field", not the deserializer's, which names the text it
read (M5c §3), since no row value reaches an error message (section 4).
The table is what each field then reads:

| Field | Reads |
|---|---|
| `Time` | Postgres `TIMESTAMPTZ`, and `TIMESTAMP` as UTC; MySQL `DATETIME` and `TIMESTAMP`; text in any RFC 3339 form `Time` reads, the fixed-width form among them (SQLite) |
| `Uuid` | Postgres `UUID`; text of 36 characters; 16 bytes (`BINARY(16)`, `BLOB`) |
| `Bytes` | Postgres `BYTEA`; MySQL `BLOB`, `BINARY`, and `VARBINARY`; SQLite `BLOB`; text as base64, as from JSON |
| `string` | as 0.1, and a `Time` or `Uuid` column as its written form |
| an integer type | as 0.1, and a MySQL `... UNSIGNED` column read as unsigned, an `Error` naming the column when the value is out of the field's range |
| others | as 0.1 |

A MySQL type name stands for its sizes too: `BLOB` for `TINYBLOB`,
`MEDIUMBLOB`, and `LONGBLOB`, and text for `TINYTEXT`, `MEDIUMTEXT`, and
`LONGTEXT`. An integer column is any integer type of the database,
MySQL's `TINYINT`, `MEDIUMINT`, and `BOOLEAN` (`TINYINT(1)`) among
them, which 0.1 read only through a cast; a `bool` field takes a
boolean column or an integer `0` or `1`, as in 0.1. A column of a type
the table does not list is an `Error` naming the column when a field
reads it, as in 0.1 §2.6, whose cast
rule now covers only what Varyk has no type for: `numeric`, `json`,
`date`, `time`, and arrays. A column no field reads is not looked at,
whatever its type: 0.1 §2.5's rule that every selected column be one
the driver decodes was `Any`'s, which converted the whole row, and it
goes with it. The README's paragraph on MySQL's unsigned integers read
wrong, and the documented cast for them, go.

A `Uuid` field reading text that is not a uuid, or a binary value that
is not 16 bytes long, is an `Error` naming the column. A SQLite `Time`
text that does not read is the same.

A scalar `T` (0.1 §2.5: a number, `bool`, or `string`, read from a row
of exactly one column) may be one of the three types too, or an
`Option` of one, read by the same table; the 0.1 rule's list grows by
them.

## 4. Connecting

`connect` and `connect_with` parse the URL once, with the concrete
driver's options, chosen by scheme as 0.1 does (`sqlite`, `postgres` or
`postgresql`, `mysql` or `mariadb`), with the same error for a driver the
build lacks. An in-memory SQLite URL keeps one connection with no idle
timeout or lifetime, as in 0.1: the database lives only while a
connection is open. Migrations run as in 0.1 (`run_direct`, the
connection closed after a failure on Postgres and MySQL). No call
panics, and no URL, password, or row value reaches an error message, as
0.1 §3 sets out.

## 5. Package layout

`src/db.rs` stays the one Rust file. The query helpers are written once,
generic over sqlx's `Database`, where sqlx's traits allow it, and once
per driver where binding and cell reading differ; the plan picks the
split. `Cargo.toml`: `varyk-std = "0.8"`; sqlx without `any` and with
`time` and `uuid`; `time` and `uuid` as direct dependencies with the
lower bounds `varyk-std` sets (`0.3.45` and `1.20`); the crate is
edition 2024 with `rust-version = "1.85"`, so cargo's resolver picks
versions that build on 1.85 for the 1.85 leg.

## 6. Testing and definition of done

- Every test of 0.1 still passes on the three databases, except those
  that pinned `Any`'s behaviour, which are rewritten:
  `a_statement_run_with_none_then_a_value_stores_the_value`, the Postgres
  text-cast tests, `a_mysql_text_column_reads_into_a_string` (kept,
  through the new type names), and
  `a_mysql_unsigned_integer_reads_through_the_documented_cast` (now read
  with no cast, and an out-of-range value an `Error`).
- New, on each of the three databases: a `Time`, a `Uuid`, and a `Bytes`
  written and read back equal, as fields of a struct, as a scalar `T`,
  and as `Option`s with `None`; a
  `Time` with a fraction and one without, ordered by `order by` in SQL;
  a Postgres `timestamp` column and a MySQL `timestamp` column read into
  a `Time` equal to the one written;
  a `Uuid` read into a `string`; a `Time` column read into a `string`
  (the written form on Postgres and MySQL, the fixed-width text on
  SQLite);
  a `None` bound into a `boolean` and a `timestamptz` column on Postgres
  with no cast, and the optional filter `($1::text is null or name =
  $1)` with `None` and with a value; 16 bytes read into a `Uuid` and
  into a `Bytes`; a MySQL `tinyint` and `boolean` read with no cast;
  a malformed `Uuid` text, a malformed SQLite time
  text, and a Postgres `infinity` timestamp, each an `Error` naming
  the column and not the value; a `select *` whose unread column is of a type the table does
  not list, read without an `Error`.
- Rust unit tests: the fixed-width time text both ways, at the bounds of
  the range; the no-secret checks of 0.1 unchanged.
- `migrations/` gains a table with `uuid`, `bytes`, and `time` columns
  whose types differ by database, in three migration folders, one per
  database, picked by the test's URL, since the column types are not
  portable (`uuid`/`char(36)`/`text`, `bytea`/`blob`/`blob`,
  `timestamptz`/`datetime(6)`/`text`). Each folder holds the whole
  history, the two portable migrations copied in and the new table, and
  every test that migrates uses the folder its URL picks, since sqlx
  refuses a folder that lacks a migration the database has already run.
- `demo/users` stores a `created_at: Time`.
- README: the Column types table rewritten, the Queries section with
  the one rule of section 2.2 in place of the `None` casts, the unsigned
  paragraph and the "every selected column" rule gone, the first
  program, its migration, and what it prints following the demo's
  `created_at`, varyk 0.8 in the status line, Install, and the
  Dockerfile, and the Versions table (`0.3 | 0.8`);
  CONTRIBUTING.md's `cargo install varyk --version '^0.8'`.
- The 0.1 spec's §1.1 first bullet, its §8 "date, uuid, bytes" item, and
  its §9 last question each gain a line pointing here.
- CI and the release workflow: `cargo install varyk --version '^0.8'`;
  `varyk-std = "0.8"` in `demo/users` too; green on SQLite, Postgres,
  and MySQL, and on 1.85.

Done when CI is green, 0.3.0 is on crates.io, and the `varyk-sql` item of
the roadmap's 5c entry in `Varyk-Lang/varyk` is checked.

## 7. Release

`feat!:`, since the package needs `varyk-std` 0.8 and a program must move
to varyk 0.8 with it. Released after varyk 0.8.0 is on crates.io, and
before `varyk-http` 0.2, whose demo needs it.

## 8. Not in this version

Columns of `numeric`, `json`, `date`, `time` of day, intervals, and
arrays without a cast; a `Uuid` stored as 16 bytes when written; time
zones other than UTC in a session; streaming large `Bytes` values in
pieces.

## 9. Open questions

- Should a `Uuid` be written as 16 bytes on MySQL and SQLite when a
  program asks for it, for the index size?

## 10. Decisions

Taken with the user on 2026-10-07:

- `Any` is dropped for concrete pools in this release, so the three
  types are native columns (M5c §12).
- A `Uuid` is 36-character text on MySQL and SQLite.
- The design of sections 2 to 6, including the untyped Postgres `NULL`
  and the unsigned MySQL integers read correctly.
