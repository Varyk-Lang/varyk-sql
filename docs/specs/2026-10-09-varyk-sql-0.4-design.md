# varyk-sql 0.4: `$1` on every database

Date: 2026-10-09.

**Status.** Implemented in 0.4.0. Extends
`2026-10-03-varyk-sql-design.md` ("0.1 §n") and
`2026-10-07-varyk-sql-0.3-design.md` ("0.3 §n"), whose rules stay in
force except where this spec replaces them. No compiler change. Varyk is
experimental and pre-1.0: anything here may change.

## 1. Summary and scope

Until 0.3 the documented placeholders are each database's own, `?` on
SQLite and MySQL and `$1` on Postgres, so a program that runs on two
databases keeps two queries and picks one with an `if` (0.1 §2.3).
(`$1` already ran on SQLite, since sqlx binds it by number, under
0.1's count of placeholders but with no check of the numbers:
`$1, $3` with two values bound `NULL` for `$3` without a word.) From 0.4 a
query written with `$1`, `$2`, … runs on all three:

```varyk
let user: Option<User> = db.first("select id, name from users where id = $1", id).await?;
```

`?` keeps working on SQLite and MySQL, so no program breaks under
MySQL's default mode (a `?` query is scanned only when it holds a `$`,
section 2). The README
leads with `$1`.

### 1.1 Decisions

- **`$n`, not `?`, as the form for every database.** Postgres has only
  `$n`, and `?` cannot be rewritten to `$n` there: jsonb's `?`, `?|`,
  and `?&` operators would be taken for placeholders, which is why sqlx
  refuses to do it. SQLite reads `$n` itself, and sqlx binds it by its
  number. MySQL has no `$` operator, so rewriting `$n` to `?` there is
  safe once quotes, quoted names, and comments are skipped.
- **Not a language feature.** Values written inside the query text
  (`${id}`, a template literal) were weighed and rejected for now: the
  `?`-and-values shape cannot be misused, since the query is a
  `&'static str` (literal-only, V0217) and the values arrive apart from it, and a template would add only a
  count check the package already does. The two-queries problem is the
  package's to solve, and this spec solves it.

## 2. Placeholders

On SQLite and MySQL a query uses either `?` or `$n` placeholders, not
both. (On Postgres `?` is a jsonb operator, so there a query may hold
both, and only `$n` are placeholders.)

A query whose text has no `$` is sent exactly as in 0.3, unscanned, so
a 0.3 query without a `$` never meets the scanner. A query with a `$`:

- **Postgres.** As in 0.1 and 0.3: the text goes to the server
  unchanged, which rejects too few values and ignores an extra one.
- **SQLite.** The package scans the text (section 2.1) and checks the
  numbers (section 2.2); the text then goes to SQLite unchanged, which
  reads `$1` as a parameter, and sqlx binds the value whose number it
  names. 0.1 §2.3's count check stays: the prepared statement's count of
  parameters (SQLite counts each distinct name once in a statement)
  must equal the number of values.
- **MySQL.** The package scans the text, checks the numbers, and
  replaces each `$n` with `?`, binding the values in the order the
  placeholders appear: `where a = $2 or b = $1` binds the second value,
  then the first, and a `$1` written twice sends its value twice. 0.1
  §2.3's count check stays: the prepared statement's count of `?` must
  equal the number of `$n` the scanner replaced.

The count check is the net under the scanner. The server's reading of
the text can differ from the scanner's: sqlx adds to the server's
`sql_mode` rather than replacing it, so `NO_BACKSLASH_ESCAPES` or
`ANSI_QUOTES` may be on; MySQL runs the text inside `/*! … */`; and
SQLite reads `$1::text` or `$1a` as a name of its own, which sqlx binds
by its leading digits, and binds a parameter numbered above the values
as `NULL` without a word. Each such difference either binds the same
value anyway (`$1::text` alone is bound by its leading digits) or
changes the server's count, which the count check turns into an `Error`
instead of wrong data, unless a `?` the scanner read as text moves the
other way in the same query (a `?` inside a `/*! */` comment or a
string beside a `$n`), which needs a literal `?` in quoted text and is
not guarded.

### 2.1 Scanning

One scanner, used on SQLite and MySQL, finds `$n` and `?` outside text
the database does not read as SQL:

- `'…'` strings and `"…"` quoted text, where a doubled quote stays
  inside; on MySQL only, a backslash inside `'…'` or `"…"` escapes the
  next character (MySQL's default mode); never inside backticks, and
  never on SQLite;
- `` `…` `` quoted names, where a doubled backtick stays inside, and on
  SQLite `[…]` too;
- comments: on SQLite `--` always starts one, to the end of the line;
  on MySQL `--` starts one only when followed by a space, a control
  character, or the end of the text, and `#` starts one; `/* … */` on
  both.

A `$n` is a `$` followed by one or more digits, where the character
before the `$` is not a letter (any non-ASCII character counts as one),
digit, `_`, or `$` (both databases allow
`$` inside a name, as in `price$1`), and the digits are not followed by
a letter, digit, `_`, or `$`. Text the scanner cannot classify is an
`Error` before anything is sent, not a guess: "the query has a quote
that never closes", or "the query has a comment that never closes".

### 2.2 Checks

A scanned query with no `$n` is a `?` query, and only 0.1's count
check applies to it. For a query with a `$n`, on SQLite and MySQL,
each of these is an `Error` before the query is sent, and leaves a `Tx`
as it was (0.1 §2.4), like the count check of 0.1 and the scanner's own
`Error`. The mixing check runs first, then the number checks:

- a query with both `?` and `$n`: "use `$1`, `$2`, … or `?`, not
  both"; a `?` inside quotes or a comment is text and does not count;
- numbers that are not exactly `$1` to `$k`, each used at least once,
  where `k` is the number of values. Checked in this order, the first
that applies giving the message: "`$0` is not a
  placeholder; they start at `$1`"; "`$` followed by a number too large
  to be a placeholder"; "the query uses `$1` to `$3` but was given 2
  values" ("uses `$1`" when the highest is `$1`); "the query skips
  `$2`".

`$n` inside quotes or a comment is text: `select '$1'` with no values
gives the string `$1`.

## 3. Package changes

- `src/db.rs` gains the scanner and the checks, and on MySQL the
  rewrite. Each private helper that runs a query (`first_on`, `all_on`,
  `run_on`; `one_on` goes through `first_on`) scans, checks, and on MySQL rewrites first,
  keeping, on MySQL only, the rewritten `String` and the values in
  placeholder order (repeated and reordered) for the call (on SQLite the
  text and the values go as given); `bind` then borrows that text
  (`bind<'q>` taking `&'q str` and giving `Bound<'q, DB>`, with the
  bounds `for<'q> DB::Arguments<'q>: IntoArguments<'q, DB>`), so a
  rewritten text needs no leak and no shared map. The scan is trivial
  next to a round trip, and sqlx's MySQL statement cache keys on the
  rewritten text. The public methods of `Pool` and `Tx` keep
  `&'static str`, which is what makes a query literal-only.
- When the count check fires on a query with a `$n`, its message is
  0.1's, naming the server's count and the number of values the caller
  gave, with a note after it: "the database read the placeholders
  differently from varyk-sql; look for `$1::text` or one `$n` in two
  statements (SQLite), or a `/*! */` comment (MySQL)".
- Nothing else changes: the surface, binding of each value (0.3 §2),
  reading (0.3 §3), and errors.

## 4. Testing and definition of done

The suite runs on all three databases as in 0.1 §6; the new tests use
`$n` queries, which no longer need an `if` per database:

- `$1` and `$2` in order, out of order (`$2 … $1`), `$1` twice, and
  out of order with a repeat (`$2 … $1 … $2`), on every database;
- `$1` inside a string, a doubled-quote string (`'it''s $1'`), each
  kind of quoted name of the database (on SQLite `"…"`, `` `…` ``, and
  `[…]`), and each kind of comment of the database, staying text; on
  SQLite `select 'a\', $1` binding (a backslash escapes nothing there);
  on MySQL `'it\'s $1'` staying text, `#`
  comments, and `select 5--$1` (a subtraction, so `$1` is a
  placeholder);
- `select 1 as price$1` not a placeholder, on SQLite and MySQL;
- both kinds of placeholder in one query, a skipped number, `$0`, a
  number too large to hold, and too many or too few values, each an `Error` on
  SQLite and MySQL (on Postgres the server's own rules apply, as in
  0.1);
- on SQLite, `$1::text` beside `$1`, and on MySQL `select $1 /*! + ?
  */` with one value, each an `Error` from the count check;
- `select '?', $1` with one value working on SQLite and MySQL: a `?`
  in a string is not mixing;
- a `?` query with a `$` inside a string (a JSON path, `'$.a'`), still
  working, and given too many values giving 0.1's message with no note;
- on Postgres, `select $1::jsonb ? 'a'` working: the text is not
  scanned, and `?` is jsonb's operator;
- a `$1` query inside a `Tx`, and a check `Error` and a scanner
  `Error` each leaving the `Tx` usable;
- an unclosed quote and an unclosed `/*` comment, each an `Error` on
  SQLite and MySQL.

Existing tests that pick a query per database with an `if` keep one
such test as it is, to cover `?`, and the tests of the count check on
a `?` query (too few, too many, no values) stay on `?` on SQLite and
MySQL; the rest whose queries differ
only in their placeholders move to `$n`; those that differ in a
Postgres cast keep their `if`. README: the Queries section leads with
`$n` on every database, keeps `?` as the SQLite and MySQL form, drops
"keeps two queries", says a `::` cast is Postgres's own syntax (so
`where ($1::text is null or name = $1)` keeps its `if`, while
`($1 is null or name = $1)` with no cast runs on SQLite and MySQL), and
its count-check bullet adds the numbering
check and the rule against mixing `?` and `$n`; the demo's note on its
`?` placeholder (before the Queries section) follows the demo, which
moves to `$n`; the Logging section's "the `?`s as written" says the
log shows the text as sent (on MySQL, the rewritten `?`s); and the
Generated ids comment that SQLite takes `$1` as well as `?` now says
every database does. In `Varyk-Lang/varyk`, `docs/roadmap.md`'s
"each database's own placeholders, passed through" changes in the
same round of pull requests. The 0.1 spec's §1.1 second bullet (the
database's own placeholders, passed through) and its §8 item on a query
spanning two placeholder styles each gain a line pointing here, as 0.3
§6 did for the rules it replaced.

Released as 0.4.0 under a `feat:` commit, with no `BREAKING CHANGE`
footer: no query that bound correctly breaks. A few that bound wrong
or were malformed now fail loudly, which the pull request description
lists (release-please writes only commit subjects to the changelog): `$1, $3`
on SQLite (`NULL` for `$3` before), `$0` on SQLite (which reached an
underflow in sqlx's binder on the connection's worker), `?` beside
`$n`, and a query holding a `$` and ending in an unclosed `/*`.

## 5. Not in this version

Named placeholders (`:name`, `@name`); an unquoted MySQL name spelled
`$1` (allowed, deprecated since MySQL 8.0.32), which the rewrite would
take for a placeholder; rewriting `?` to `$n` on
Postgres; `$n` in a statement that defines a function or trigger body
on MySQL (the scanner reads the body as SQL, which is the database's own
reading of it); the same `$1` in two statements of one query text on
SQLite (sqlx counts parameters over every statement, so the count
check refuses it).
